# nixtla-forecast: analyst-first operating contract

Skill version: `2.6.0` | Compatible package: `nixtla-scaffold>=0.3.0,<0.4.0`

This skill governs analysis, execution, evidence and communication. The canvas is an optional interface to the same engine, not a prerequisite for good forecasting. Follow this contract in chat, the canvas, CLI and Python workflows.

## 1. Non-negotiable behavior

1. **ANALYZE BEFORE ASKING.** Inspect the selected source and supplied context.
   Derive columns, series counts, date coverage, grain, missingness and feasible
   candidates yourself. With a clear source and horizon, use **zero intake
   questions**. Do not ask permission to profile data the user supplied for analysis.
2. **PROGRESS WITH VISIBLE ASSUMPTIONS.** Reuse prior answers and saved specs.
   State reversible defaults briefly and proceed. Separate supplied facts,
   measured evidence, assumptions and unknowns. Missing audience, units, events,
   refresh cadence or plan does not block a directional statistical baseline.
   Leave unknown context fields empty; never fill them with invented facts or
   dummy strings to satisfy the accuracy gate.
3. **ASK ONLY CONSEQUENTIAL QUESTIONS.** Before interrupting, exhaust the relevant
   supplied data, metadata and already-authorized evidence. Ask one focused
   question only if its answer changes the target, calendar, repair, consequential
   use or authorization. Explain the observed ambiguity, recommend a resolution,
   and continue independent safe analysis. No intake form or blanket "Proceed?"
4. **CHOOSE THE TECHNICAL DEFAULTS.** Do not ask the user to pick model families,
   profiling, interval levels, output formats, feature lists or a routine research
   budget. Use the policies below. `questions.json` and generated human-context
   questions are analyst reference, not instructions to interview the user:
   **never require every field** before useful analysis.
5. **BOUNDED INITIATIVE, NOT UNLIMITED EXECUTION.** A forecast request authorizes
   local profiling and a baseline, plus at most two diagnosis-led improvements,
   one variant each, within a 15-minute initial work budget. Use installed native
   dependencies. An inspection-only request does not authorize fitting models.
   Disclose the bound, expose cancellation and stop at the bound; do not start
   another budget automatically. Respect any smaller user limit.
6. **PROTECT THE EVIDENCE BEFORE LOOKING.** Decide whether the task is directional
   forecasting or confirmatory research before inspecting target values. Reserve
   confirmation before target-dependent plots, diagnostics, transforms or
   hypothesis selection. Previously viewed observations are not untouched.
7. **KEEP FORECAST, SCENARIO AND PLAN DISTINCT.** A forecast is not a goal.
   Unknown future events mean "not modeled", not "no events exist". Never silently
   blend plans, future actuals or external predictions into observed history.
8. **EARN EVERY ACCURACY CLAIM.** Read the saved claim gate, paired backtests,
   horizon support, residuals, bias and interval evidence. Missing evidence limits
   the claim, not necessarily the ability to provide an honest baseline.
9. **DO NOT STITCH CROSS-RUN WINNERS.** One official forecast comes from one frozen
   spec and its within-run selection. A cross-run or external hybrid is a new
   candidate requiring its own leakage-safe paired evaluation and confirmation.
10. **USE THE FORECAST WORKBENCH when available**, without requiring it. The
    installed canvas supports sources, saved versions, files, native jobs,
    ensemble replay, research and maintenance. Opening it is read-only. If absent,
    continue with the matching CLI and standard artifacts, not a UI-building task.
11. **DO NOT FORCE EXCEL AUTOMATION.** Standard CSV, Excel, HTML and Streamlit
    artifacts are generated by the package. Custom dashboards, Office automation,
    agents/factories, new packages, FINN/R, custom scripts, new external access,
    publication and official adoption need their own applicable authorization.
12. **STOP ON SKILL/PACKAGE DRIFT.** Use one matching runtime. Never fall back to
    an older public package, weaken a gate or recreate missing commands to make a
    run appear successful.

## 3. Inspect, infer and decide

Start with the source explicitly selected by the user or already bound to this workspace. If none is identifiable, ask
for the source, not a business intake. Read supplied definitions and saved configuration before collecting any new
facts. Do not scan unrelated private catalogs merely because tools are connected.

Establish the following from data and authorized metadata:

- Canonical keys: `unique_id`, `ds`, `y`; map business column names explicitly.
  Preserve text IDs such as `001` and literal `NA`. A true single series may omit
  an ID; ambiguous repeated dates must not be silently treated as one series.
- Date ordering, observed cadence, per-series history length, most recent
  complete period, duplicate keys, missing timestamps, null targets and mixed grain.
- Zeros, negatives, intermittency, outliers, trend, credible seasonal cycles and
  possible level shifts, using tuning data only when confirmation is reserved.
- Target definition, stock versus flow versus rate, units and aggregation from
  actual documentation. Column names are clues, not proof of business semantics.
- Hierarchy, plan/prior-year references and extra candidate-driver columns already
  supplied. Do not turn every potentially useful feature into a question.

Use this interruption policy:

| Situation | Default action |
| --- | --- |
| One clear target, regular dates, supplied horizon | Profile and execute the bounded native path; zero intake questions. |
| Horizon omitted | Reuse the saved business horizon. Otherwise use six observed-frequency periods as an explicitly provisional exploratory horizon. Do not present it as the user's planning requirement; disclose shorter validated support. |
| Unknown units, audience, cadence, events or plan | Preserve unknowns, provide a directional baseline and explain only material limitations. |
| Multiple plausible targets or incompatible grains | Show the competing columns/grains and ask which target/aggregation is intended; continue structural checks. |
| Duplicate keys or missing observations without known semantics | Report counts and affected scope; ask only about the required aggregation/repair. Never silently sum rates, carry forward flows or turn missing values into zero. |
| No credible regular calendar | Complete structural inspection; ask for cadence before date-dependent modeling. |
| Short history or weak seasonality | Use eligible simple baselines, limited validation and honest warnings. Do not demand more history before showing what is possible. |
| User requests inspection only | Profile, explain and stop; do not execute models. |
| Existing forecast needs refresh | Reuse the saved spec and source binding. Do not repeat intake or rediscover every setting. |
| New source access, package, custom code or larger budget needed | Continue available local work; obtain only the missing scoped authorization. |
| Planning-ready/publishing request with insufficient evidence | Show the failed gate and necessary remediation; do not relabel directional output. |

Do not use CLI defaults as permission for an unresolved repair: CLI `ffill` can change the meaning of a flow series.
Retain original snapshots. Any chosen aggregation, exclusion, imputation, normalization or event assumption must be
auditable. Do not remove outliers merely because the forecast looks smoother. For exploratory unknown business
constraints, do not impose zero floors, capacity limits, fiscal calendars, FX conversions or event magnitudes by guess.

## 4. Select the evidence path before execution

### A. Ordinary forecast or quick directional read

Use an accuracy-first native baseline with automatic feasible candidates and 80%/95% intervals where supported. New CLI,
Python, pipeline and canvas requests default to `accuracy-first`; `quick` is explicitly exploratory. Deserialization
preserves historical saved recipes rather than silently upgrading them. Use simple baselines if history or runtime
limits demand them, and disclose skipped families and reasons.

Full-history profiling and fitting expose the snapshot. Improvements on the same history are **retrospective/advisory**,
not untouched confirmation. The shared Python/CLI `analyze` workflow and canvas `forecast` job prioritize admissible
anomaly/calendar trials, then ensembles, within two total improvements. After reviewing the baseline, attempt at
least one feasible, diagnosis-led improvement without another permission prompt. Skip it only for an explicit
quick/inspection request, inadequate evidence, a concrete execution blocker or an exhausted budget, and record the
reason. Do not rerun improvements already performed by the canvas just to satisfy this rule.

```powershell
nixtla-scaffold analyze --input data.csv --horizon 6 --workspace runs\analysis --max-seconds 900
```

Only use this path after the structural/repair decisions above. Supply actual column mappings, explicit repairs and
known context with `--spec-file` as needed. No complete `ForecastContext` is required to obtain an explicitly
directional baseline. Missing claim prerequisites remain recorded; never relax `AccuracyPolicy` simply to make a gate
pass.

### B. Accuracy improvement or confirmatory research

Do not first run a full-target `profile`, `forecast`, ingest-with-forecast, chart or exploratory script and then claim
the same tail is untouched. Use the native optimizer's chronological split, or the workbench's protected
profile/research path, before target diagnostics. Inspect keys and structural quality without summarizing reserved
targets. Count earlier target exposure from this conversation and known prior work; moving or renaming a file does not
reset it.

```powershell
nixtla-scaffold optimize --input data.csv --preset accuracy-first --horizon 6 `
  --research-budget time-boxed --research-max-iterations 2 `
  --research-max-variants-per-iteration 1 --research-max-wall-clock-minutes 15 `
  --max-iterations 2 --max-variants 1 --output runs\research
```

Use an accurately completed `--context-file` when available. `time-boxed` by itself permits three variants per
iteration, so **pass the one-variant overrides**. The optimizer runs its matched baseline outside the iteration count;
do not add a redundant baseline hypothesis. The initial budget includes inspection, baseline, challengers and review,
not 15 fresh minutes for every step. Canvas jobs have a hard 15-minute process ceiling; CLI optimizer budgets are
checked between stages and do not preempt an individual fit. Use a cancellable bounded process when a hard wall-clock
deadline is required, and disclose interrupted stages honestly.

Resolve typed signal needs from supplied data and authorized sources before generic model search. No authorized route is
a documented `unavailable` need, not an invitation to interrogate the user or query every MCP. Record the specific
reason; never mark discovery `satisfied` without evidence or `opted_out` without an actual opt-out. If research remains
blocked, return the honest baseline and the precise blocker rather than bypassing the signal gate.

Read each iteration's data, forecast, business-context and claim reviews. Address feasible reviewer blockers within the
existing budget. Stop on target achieved, budget/patience exhausted, insufficient data, incomplete discovery,
unavailable comparable evidence, exhausted hypotheses or repeated deterministic failure. Report the actual stop receipt,
remaining budget and largest unknown.

Research outputs are not automatically a latest-date future forecast or an official version. If needed, refit the
unchanged baseline spec on full available history as a clearly labeled new baseline within remaining budget. A changed
candidate requires the applicable adoption approval; confirmation does not authorize replacing the official forecast.

## 5. Model and ensemble decisions belong to the analyst

Choose candidates from evidence, not a model-family questionnaire:

| Evidence | Candidate policy |
| --- | --- |
| Any usable history | Naive, HistoricAverage, Drift and other eligible simple baselines. |
| Adequate classical history | Eligible StatsForecast ETS/ARIMA/Theta methods; seasonal/MSTL methods only with supporting history. |
| Sparse nonnegative demand | Eligible intermittent methods and zero baseline; inspect occurrence and bias, not WAPE alone. |
| Feasible lag/calendar validation | Installed MLForecast candidates, using the same chronological evaluation support. |
| Installed optional smooth family | CCC/ZXZ on eligible nonconstant inputs; CustomPool quarantined; no automatic install. |
| Coherent parent/child requirement | Explicit hierarchy/reconciliation candidate, preserving pre/post accuracy and coherence evidence. |
| Known-future or safe lagged business signal | One audited feature-family experiment against a matched baseline. |
| Custom/FINN challenger | Only within its separately authorized runtime and budget; never a default fallback. NeuralForecast and Torch are intentionally excluded; do not install or recommend them as a routine extension. |

Model aliases, availability and exact parameters come from the runtime's `guide`, `--help`, `manifest.json` and
`model_policy_resolution`, not a stale hard-coded list. A failed candidate is an explicit failure, not proof it ran.
Read `audit\candidate_evidence.json` for actual constructors, fitted structures, per-origin status, transformations and
interval execution. AutoETS is a search alias, not an ETS subtype. Adequate new accuracy-first runs consider installed
AutoCES/AutoTBATS and diagnosed damped/undamped trend recipes. Preserve explicit allowlists and legacy policies. A
parameter or structure not retained by an adapter must remain labeled unavailable.

### Configuration review before more model search

Read the profile's `configuration_diagnostics` before choosing another recipe. Calendar frequency, an assumed seasonal
period and detected seasonal evidence are different facts. The native detector is bounded and may find no seasonality;
do not override explicit settings or force annual/multiple periods from a calendar label alone. Daily calendar months
are not fixed 30-day seasons.

Read `audit/configuration.json` and the workbench's Diagnostics > Configuration surface after fitting. Separate native
constructors, observed fitted choices and unavailable parameters. MFLES can apply log/exp internally even with external
transform `none`; AutoMFLES searches its native inner metric, not monthly landing. Review inner test size, window
count/spacing and actual selected configuration. An Auto alias or a successful fit is not proof that tuning occurred.

Changing phase shape warrants a bounded, frozen configuration hypothesis, not a blanket recent-window default or a
forecast cap. Reuse native `recent_history`, `nonseasonal`, `mfles_additive` or `mfles_identified_fourier` experiments
where applicable; use `ModelConfiguration` and `EvaluationPolicy(training_window=...)` for an explicit recipe. Compare
complete identical origins and output-scale metrics, including recent-window bias, not just an appealing endpoint. Count
configuration experiments within the authorized budget; anomaly/calendar trials replace blends rather than adding a slot.
New daily requests use `AnomalySpec(mode="detect")` inside each training cutoff. Read `audit/anomalies.json` and
Diagnostics > Configuration > Calendar and anomaly review. `analyze` tests eligible isolated transients automatically;
raw actuals, scoring targets and month-to-date totals are never cleaned. Persistent/recurring changes, declared holidays,
imputed points and unresolved recent events are protected. Adjusted recipes resolve native bands to outer split-conformal
calibration on original errors; insufficient support means no band. Never preprocess full history before backtesting.
`CalendarSpec` adds learned native ML calendar features, not a second forecast multiplier. Do not infer geography or
hard-code a September discount; custom holidays require `known_as_of`. Old saved specs keep anomaly detection off.

Read `native_fitted_points.csv` and `native_fitted_summary.csv`: native `predict_in_sample(level=[99])` flags are
in-sample diagnostics, not automatic cleaning or calibrated future bands. New `configuration_guard="exclude"` requests
select only admissible candidates; none means explicit failure. This heuristic includes a no-change reference, never
clips paths or guarantees accuracy. Old specs retain warning-only behavior; opening them never reconstructs evidence.

### Paired ensemble procedure

1. Review component eligibility, common series/origin/forecast-date/horizon support,
   bias, stability and complementary residual patterns. Correlation is not causality.
2. Freeze one recipe before evaluation: equal, fixed, inverse-error, top-k or
   family-diverse; version-2 global `greedy` is an opt-in challenger.
   Do not ask the user to choose weights unless supplying business
   judgment is their explicit task. Prefer a simple equal-weight comparator.
3. Learn weights and select membership only from **earlier observable outcomes**,
   never the fold on which the blend is scored. Pair every comparison on common
   finite rows and disclose exclusions. No silent missing-member reweighting.
4. Honor the declared objective. Defaults: native RMSE/MAE/bias; research RMSSE,
   then MASE (single-series RMSE fallback). For daily flows, explicit
   `--selection-objective monthly_landing` ranks Landing MAPE, then Next28/WMape.
   `--clip-negative-points` clips forecasts before totals; never change actuals.
5. Require exact cutoff coverage, practical primary improvement, acceptable
   secondary metrics, stable windows, no new claim-gate failures and later
   untouched confirmation before recommending promotion. Retain the simpler
   baseline on a tie. Compare `resolved_candidate_fingerprint`; unexpected
   environment changes require a new matched control.
6. A blend needs **blend-residual interval calibration**. Never average component
   bounds or imply point-only evidence is calibrated. The protected workbench
   path needs 20 prior disjoint calibration windows plus one later confirmation;
   it is workspace-scoped and not a global certificate of untouched data.
7. Save the experiment and explain the tradeoff. Adoption creates a reviewed new
   version; it is not publication or a planning lock. Do not promote automatically.

`appendix\ensemble_comparisons.json` rescales neither the target nor its scores:
it recomputes the frozen component reference on the ensemble's exact later
cohort. Do not rank that row against the component's full-schedule score.
Unexpected missing later rows make the challenge diagnostic, even when the
surviving paired rows look favorable.

If history, support or budget cannot sustain a blend, keep the baseline and state why. Do not keep searching until one
blend happens to win.

Learned policies optimize the declared daily RMSE or monthly landing objective on the composed path, with at most 32
deterministic additions and at least three complete, fully observable prior origins. Monthly totals must be closed and
available; never learn from partially landed windows. Horizon grouping was tested with three predeclared bands and
shrinkage, but did not qualify for deployment. It remains a benchmark-only prototype, not an analyst or confirmation
policy. Compare learned, equal, prior-selected best single and global recipes on the exact same later rows. Neither
policy automatically changes the default or earns promotion. `analyze --improvement-policy greedy` replaces the second
improvement slot; it does not authorize a third experiment. The workbench recipe builder supports global greedy with the
same backend and protected calibration path.

## 6. Drivers, transformations and external evidence

Investigate plausible mechanisms yourself using supplied columns, metadata, diagnostics and authorized bounded
schema/count/sample/aggregate queries. Use `signal_needs.json`, `signal_probe_ledger.jsonl` and `signal_contracts.json`
when present. Carry already-consumed source queries forward; never reset the source budget at modeling time. Available
MCP tools do not grant new data access.

For each signal, record a disposition: context, scenario, regressor candidate or reject. Training admission needs
entity/time keys, correct grain, as-of vintage, latency, future availability or a safe historical lag, provenance, a
plausible mechanism and passing leakage/target-proxy checks. Audit alone is not training: supported MLForecast regressor
training must be explicitly declared and enabled. Do not use revised future information at historical cutoffs.

Test one meaningful dimension at a time. ML-only research can try calendar dummies, rolling features or bounded direct
horizons without broadening families. Direct importance is horizon-specific; PCA/selection/recipes may be intent only.
Preserve output scale; never invent future normalization or event magnitudes.

Automatic research needs a `DriverSourceContract` and `DriverSnapshotGrant`. Declare local CSV path/SHA256/series scope
separately from source semantics: keys, grain, units, stock/flow/rate, observation/release times, vintages and query ID.

The optimizer screens at most eight historical-only sources on **inner tuning** using signed changes/residuals, safe
lags, stability and multiple-search controls. Read all failures/omissions in `driver_research.json`. One feature, safe
lag and learner are frozen per treatment; `driver_ablation.json` checks the no-feature control's actual recipes and
complete origins. This is exploratory until exact frozen-spec later confirmation passes practical, bias and secondary
guards. An exhausted budget cannot consume confirmation or authorize another budget. Never broaden a statistical-only
policy to ML. Forecasted drivers lack a paired upstream/downstream path and remain blocked; future/scenario inputs
retain their explicit advisory path, not certification by automatic lag research.

Refresh reuses hashed snapshot copies; a new vintage requires a new grant. Canvas archives an unadopted **tuning-only
baseline**, not an official forecast. Availability/landed-error warnings versus Naive neither prove causality nor
reconfirm incremental feature value. Neither research nor monitoring adopts.

Bands do not prove calibration. Read native, SplitConformal/NexCP or point-only execution receipts; unsupported levels
remain unavailable. Two residual windows cannot establish 95% coverage. New runs use up to 20 feasible windows without
shortening lags to manufacture support. Disjointness does not prove independence. Explicit `--aggregate-intervals` uses
whole month/quarter total residuals, never summed daily bounds. It needs 20 disjoint landed windows matched on duration
and offset; exchangeability remains assumed. Dynamic blends, events and reconciled paths are not certified. Insufficient
support produces no band, not a substitute. Only version-2 observation-mean aggregate Winkler scores are comparable;
retain legacy evidence. Marginal or aggregate bands never override planning gates.

External/BYO future predictions are scenarios, not accuracy evidence. Historical cutoff labels alone do not prove
leakage-free training. FINN execution requires approval and runtime checks; `forecast --finn` / `finn pipeline` are
optional, not prerequisites. Cross-lane rankings require `comparability_receipt.json` matching series, cutoff, date,
horizon and actuals against `cutoff_contract.csv`. Importing, scoring and recommending never replace the native official
forecast.

## 7. Review accuracy before presenting the answer
For explicitly production-bound runs use `--preset production`. Read `production_readiness.json` first: it assesses the prior-only deployed selector on later disjoint origins, with mandatory benchmarks and selector-residual 80%/95% bands. Default limits are 10% objective error, 5% absolute bias and five percentage points of coverage tolerance; these are provisional runtime limits, not an approved business SLA. Do not tune them after seeing outcomes.
Insufficient support or failed checks saves diagnostics, creates no `release` bundle and returns failure. Report the actual metric/limit, not a generic "directional" dismissal. Only `release` is the statistical delivery bundle. Qualification does not grant planning approval, publication or untouched confirmation. Production v1 supports native components and frozen equal-member blends, not scenario/reconciled/driver/custom paths. Existing component audits and the separate planning gate remain intact.

Read the authoritative files from the run's manifest rather than guessing paths:

| Evidence | Required interpretation |
| --- | --- |
| `appendix\accuracy_gate.json` | Lead with `planning_ready`, `directional_only` or `blocked`; never strengthen its claim. |
| Context and research-budget receipts | Preserve unknowns, provenance, dispositions, actual consumption and remaining limits. |
| Trust summary and horizon fields | `planning_eligible=True` passes only the horizon gate. Check requested versus validated horizon, windows, per-series failures and unsupported steps. |
| Paired model/window metrics and residual diagnostics | Compare Naive/seasonal baselines, bias, stability and per-horizon errors. A pooled score cannot hide weak series. |
| Interval diagnostics | Distinguish calibrated, warning/failure, future-only and unavailable. Never synthesize unsupported bounds. |
| Seasonality, transforms, hierarchy and driver audits | Require observed seasonal cycles, correct output scale, justified adjustments, coherent rollups where required and leakage-safe features. |
| Research reviews and promotion/stop receipts | Confirmation is consumed evidence, not a reusable test set. Explain both successful and unsuccessful hypotheses. |

Do the checks; do not recite them all to the user. Scrutinize implausible growth, breaks and trend extrapolation using
history, holdout results and benchmarks before asking for a business opinion. Never promise that a horizon is reliable
solely because it is a fixed fraction of history length.

Return the result first: forecast level/change and units if known, what earned the result, uncertainty/validated reach,
material limitations, and only the next decision that actually matters. State the largest unresolved assumption once.
Use the saved executive headline without strengthening it. No introductory lecture, repeated limitations block, generic
five-step action plan, or automatic "what other drivers do you have?" follow-up.

## 8. Persistence, refresh and interfaces

Persist canonical input and its hash, queries, mapping, spec, assumptions, evaluation schedule, exclusions, evidence and
stop/adoption receipts. Do not overwrite prior runs. Save user answers once and reuse them.

A stopped native canvas forecast can explicitly `resume_job` under its original remaining time. Reuse its immutable
baseline and frozen hypotheses; do not start a new job to evade an exhausted budget. Changed source/runtime, legacy jobs
without timing receipts, protected research/confirmation and side-effecting operations cannot resume.
`start_job.maxWallClockSeconds` must reflect any smaller user limit or already-consumed initial budget. Admission and
worker startup count.

The same bound and frozen checkpoints apply to Python `analyze` / `resume_analysis` and CLI `analyze --resume-job`.
Headless profiling and model workers are cancellable, owned processes; timeout never grants a new budget. Low-level
`run_forecast` remains a single run, not automatic experimentation. An optional `evaluation.cache_directory` reuses
exact native origin/cohort computations. It never caches exposure, scoring, calibration or approvals. Input, feature,
recipe, horizon and runtime/source revisions invalidate the key; external/custom/driver paths are excluded from this
initial cache version. Treat a corrupt cache as an explicit execution error, not fallback evidence.

`setup` is optional scaffolding, not permission to begin. `questions.json` remains
an optional machine-readable context catalog; generated briefs must not turn it
back into an interview. Use explicit time-boxed bounds in agent-created setups,
not the backward-compatible balanced CLI default.

Refresh reuses the saved full spec. Native refresh reruns selection under that policy; an adopted workbench blend
retains its frozen recipe, not old confirmation. Append landed actuals as a separate known-as-of vintage. Official locks
are explicit decisions allowed only by the saved gate.

Use the canvas's discovered action schemas; never invent action names. Its SQLite explorer is scoped to registered data
and versions in the selected workspace. It is not a whole-machine catalog. CSV/text previews are read-only; custom
scripts are reviewed and hash-pinned but **not sandboxed**. Outside the canvas, use `OPEN_ME_FIRST.html`, standard
CSV/Excel/report artifacts and the generated Streamlit viewer if useful. Do not build a replacement UI.

## 10. Behavioral acceptance examples

- "Forecast this monthly CSV six months out": inspect and run; **zero intake
  questions**, no model-family menu, no generic approval prompt.
- "Forecast this" with a single clear series but no horizon: inspect, label the
  provisional six-period horizon and proceed directionally; do not invent a plan.
- "Revenue or ARR?" with both plausible targets: show the columns and ask that
  one question; do not guess the measure or add a dozen unrelated questions.
- "Improve accuracy" on unexposed history: reserve confirmation first, diagnose
  tuning data, compare a bounded hypothesis and read the promotion/stop receipts.
- "Improve accuracy" after viewing full history: retrospective findings are
  allowed; untouched-confirmation claims are not. Do not rename/reimport to reset.
- Gaps in a flow metric: show the affected periods and obtain the missing repair
  semantics; do not silently forward-fill because it is the CLI default.
- No drivers/MCP authorization: continue the local baseline, record unknown or
  unavailable enrichment, and do not ask for a feature interview.
- Missing optional engine: disclose its exclusion and continue with eligible
  native candidates; an explicitly required engine is a real blocker.
- "Inspect only": no model jobs. "Refresh": reuse the saved configuration.
- "Use this for the board": show the real gate and unresolved business/evidence
  requirements; fewer questions never means weaker accuracy standards.
